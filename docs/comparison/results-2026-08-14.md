**The `review` arm got the same brief as `ctrl`, word for word, plus one added
sentence: "review your own work once, and fix what you think should be fixed".**
No rule sheet, no checkers, and **deliberately no mention of security or of any

## What the numbers say

1. **Gate findings: 16 → 0.** The control arm failed nearly the same rules every
   time — no debug entrypoint (5/5) and delete-means-soft-delete (5/5). The rules
   arm has none left, which is **expected**: looping the doctor until clean is
   part of its procedure. This number confirms that the loop works; it proves
   nothing about quality.
2. **ASVS: 7.6 → 9.8 of the applicable items.** This one carries more weight,
   because **no scanner in the bundle checks any of these items** — there was no
   gate an agent could see and write toward. (It is **not** independent of what
   was *taught*, though — limitation 2 below.) **The solid part is the
   consistency, not the mean**: the control arm failed two items **5/5, the same
   two every time**:
   - `V14.1.3` — a debug server started in the entrypoint's main guard, the same
     hole a scanner caught in the reference implementation before the rule against
     it existed
   - `V6.4.1` — a signing key read from the environment **with a guessable
     fallback**; in production that is forgeable sessions for the whole system
3. **Roughly six times the code** (327–427 lines against 1972–3026). The rules arm
   wrote a service layer, an audit chain, soft delete, migrations, decision
   records, a data-classification document. **That is a cost, not a score.** A
   project that does not need those things pays more for them.

## What the numbers do not say, and must be read beside

- **The outside scanner flagged the rules arm four times and the control arm
  never.** All four are the same rule at the same place: a function computing a
  rate-limit key that returns a hash of a formatted string — **not a view, no
  route decorator, and no user input reaching the result**. A false positive.
  That it appears on one side only is **not because that side is worse, but
  because only that side wrote the feature the rule misreads** (a per-username
  login quota). More code means more surface for a heuristic to misjudge, which
  is a side effect to state rather than hide.
- **No app was ever run**, on any arm, by the brief. What is measured is traces in
  files, not behaviour. The rules arm wrote tests in 4 of 5 apps, but **none of
  them was run or put through a mutation test**, which is the rule sheet's own
  first rule — three agents recorded that about themselves, openly.
- **Doctor rounds cannot be compared across arms**, since the control arm has no
  such loop; and **inside the rules arm they cannot be compared either**: 2, 3, 3,
  4, 2 rounds, but one app installed the checkers *before* writing code in order
  to read them first (a deviation from the procedure), while two were clean on
  the first round and spent the rest confirming after their own mutation testing.
  **A "round" counts a different thing for each of them.**
- **The doctor's first finding was the same thing in 3 of 5 apps**: a comment in a
  template *quoting the forbidden construct to explain why it is not used*, which
  the line-based template scanner then matched. **That is a defect in the checker,
  not in the code** — the entrypoint scanner reads syntax and has no such problem.
  All three chose to change their own code rather than weaken the check, which was
  right; but **the work left over is teaching that scanner to tell a comment from
  markup**, not asking people to keep avoiding a word.

## What this round exposed about *the instrument itself*

The first version of the probe reported the rules arm as **worse** on three
items. All three were the probe's fault:

| symptom | cause |
|---|---|
| every app in the rules arm "forgot to check ownership" | it read the framework's *web session* accessor as a database lookup, and punished a shared `by_id(model, id)` helper whose callers all check ownership — **scoring the worse idiom higher** |
| "a signing key hardcoded" | it found a fake key in a test fixture — **punishing the arm that wrote tests** |
| "no password length rule" / "no CSRF" / "a debug console" | tied to one idiom each: the variable had to be named for passwords · the token had to be the raw field, so a macro was invisible · and a text search for the debug flag matched **a docstring saying the file has none** |

All of them are fixed, with fixtures holding them open — the probe's tests carry
three idioms: the direct one, a form validator, and a service layer.

**The lesson that applies to every measurement after this one:** when the person
measuring owns the thing measured, the dangerous error is not the number that
flatters them — that one is doubted immediately. It is **the number that
contradicts them, which gets believed at once because it looks honest.** Stopping
at the first result here would have published that the rules made things worse on
three items, and all three were wrong.

## Limits of the *experiment's design*, as distinct from the instrument's

These do not make the numbers wrong. They make **what the numbers are evidence
for** narrower than a quick read suggests:

1. **The rules arm got an extra pass that the control arm did not.** Looping the
   doctor means going back over your own work; the control arm wrote once, by the
   brief. The difference measured is therefore of **"rules + checkers + having a
   second pass" together**, and two arms cannot separate them → **closed by the
   third arm**, below.
2. **The ten items were chosen by the same person who wrote the rules.** It is
   true that no checker tests these items, so no agent could write toward a gate
   it could see — but the rule sheet does discuss secrets, CSRF and ownership
   directly. **So this axis is independent of "the gates an agent saw", not of
   "what it was taught".** The genuinely independent axis is the outside scanner,
   which found no difference of substance (see the false positive above).
3. **N = 5 per arm, with no statistical treatment.** Means of 7.6 and 9.8 over
   groups of five prove nothing by themselves. What can be asserted is **a
   repeated pattern** — the control arm failing the same two items in all five
   apps — never the distance between two averages.

## What the third arm attributes to what

The ASVS gap between control and rules is **2.2 points**. The `review` arm, which
received one sentence and nothing else, closes **1.6 of them — about three
quarters** — leaving roughly **0.6 points** that belong to the rules themselves.

**What a review pass found on its own, with nobody pointing at it** (from the
agents' own reports): a timing oracle at login (3 of 5) · foreign-key enforcement
never switched on in SQLite (3) · a unique index that was case-sensitive while
login compared case-insensitively (2) · session fixation · a password length
ceiling · a debug flag left set in an environment file.

**What a review pass did not find, and where the rules still differ:**

| item | control | +review | rules |
|---|---|---|---|
| delete means soft delete | fails 5/5 | **fails 5/5** | passes 5/5 |
| no debug entrypoint | fails 5/5 | fails 2/5 | passes 5/5 |
| `V6.4.1` no fallback secret in code | fails 5/5 | fails 2/5 | passes 5/5 |
| consistency (the arm's worst app) | 7/10 | 8/10 | 9/10 |

**Soft delete is the sharpest line**: not one app in the review arm thought of it
by itself, because it is not a *mistake* visible when re-reading your own code —
**it is a convention of a project**, and nobody guesses a convention nobody wrote
down. What *ordinary security sense* can reach, the review pass had already
collected.

## What can be claimed, after the third arm

In the conditions recorded above:

1. **Giving an agent the rule sheet, the checkers and the loop does change the
   code, measurably** — still true (ASVS 7.6 → 9.8 · gate findings 16 → 0 · and
   this arm's worst app is better than any other arm's worst).
2. **But most of the difference on the ASVS axis is not from the rules' content.**
   It comes from **having a second pass**, which one sentence commands and which
   needs no scaffolding at all. If the goal is to raise the security floor of
   generated code, **the cheapest thing by far is to require a review pass, not to
   export sixty rules.**
3. **What scaffolding gives that nothing else did is a project's own conventions,
   and consistency** — soft delete, an audit chain, a service layer, data
   classification. Nobody invents those unprompted, and this arm's results are the
   least spread of the three.
4. The cost is unchanged: about 4.5× the code of the review arm, and about 6.6×
   the control arm.

**Had the first version of this report been used to decide anything, it would have
oversold the scaffolding by nearly threefold** on the axis a reader cares about
most — and nothing in the two-arm data gave any signal at all.
